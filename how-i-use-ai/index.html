How I use AI

The ideas behind how I work with an AI agent, each with the mechanism that makes it hold in practice and a smaller version you can try in your own setup with any capable model.

1The short version

I run my work through an AI agent, and what makes it useful comes from a few ideas that would work with any capable model. When I correct the agent, the correction is written to a file that the next run reads first, so I make each correction once. It may read widely, but nothing leaves the machine without my approval, and a check that runs outside the model enforces it. Code and a second reader check the work before I see it, because the errors that matter are the ones that read well. I state each preference once as a short named rule and attach it by name. It interrupts me only where a person is needed, and it batches its questions. Work that cannot happen yet waits on disk with what it depends on, and private data stays out of anything shared because of where it is stored. Each section below takes one of these ideas, explains the mechanism I use, and ends with a smaller version you can try.

2Corrections that persist

A model starts each session knowing only what it is given. A correction I make in a chat lasts until the session ends, and the next week I would make it again. So everything that should outlast a session goes into a file the agent reads before it starts: the instructions for each recurring task, the rules I care about, and the lessons each task has earned.

Each recurring task has its instructions in one file and its lessons in a second file beside it. After I correct a run, the agent writes the lesson into that second file during the same run and tells me in one line that it did. Every later run reads the lessons before the instructions, and a lesson wins where the two disagree. A lesson that holds twice, or that I state as a rule, moves into the instructions themselves, and a lesson that goes stale is struck through with the date and the reason, so the file keeps its own history.

A useful lesson records what I changed the output to. "Lead the email with the number" tells the next run what to do, while "the output was too long" records only a mood. One ambiguous edit is never a lesson, since a guessed preference is how a system like this drifts away from what I want, so the agent waits for a second instance or asks me. A fact about one company or one person stays out of the lessons, and about twenty active lessons is the ceiling, because past that the file has become a second copy of the instructions.

Preferences about me get the same treatment in their own file, written as dated directives. When a preference changes, the old line is marked superseded and the new one is written in its place, so two contradictory rules never stand at once. I also keep, word for word, the prompts that show how I frame a problem, such as a spec or a correction with its reason, because a better model can read an original again and draw more from it than from today's summary. Most prompts are routine and are not kept.

Try it

Keep one notes file for each task you give a model more than twice. When you correct it, ask it to add one line to the notes saying what to do differently next time, and paste the notes above your request when you start that task again. dexter's protocol has the rules for writing, promoting and retiring a lesson.

3Approval at the edge of the machine

If the agent misreads a file or a web page, nothing outside my machine changes. A sent email, a public post or a submitted form cannot be called back, and a public push can be copied within minutes. So I draw the line at the edge of the machine. The agent may read files, the web, and my mail and calendar through connectors, and it may carry any outward act up to its final step: an email waits in my drafts, an application waits at the Submit button, and a food order waits at Place Order, where I make the last click.

A rule written in a prompt is one more instruction a model can lose in a long session, so I enforce this one with a hook, a script that Claude Code runs before every tool call. The hook is registered in the one settings file that every way I run the agent reads, so it covers the terminal, the desktop app, scheduled jobs and the bot I message from my phone. Before each call, a short policy gives one of three answers. A recoverable act, such as a push or a deleted folder, goes ahead and is flagged for a daily review. A message to someone else, a force push or an edit to the hook itself waits for my yes. A few acts are refused outright, such as deleting the home directory or repeating the same call eight times in a row. When nobody is there to answer, as in a scheduled run, a question becomes a refusal that leaves the act for me.

The hook also writes every prompt and tool call to a local log with secrets removed, and new rules come from that log. I add a rule after the log shows a mistake that actually happened, since a refusal that fires on ordinary work costs more than the warning it replaced. Before turning a policy on, I replay it against past sessions to see what it would have done. The first version, replayed over a week of my sessions, would have held 26 of 17,300 tool calls, and every one of the 26 was a real publish, force push, repository change or edit to the hook.

Some sends do not look like sends. Typing into a chat app is one, because a click that misses the search box turns the query into a message to the whole channel. Chat apps are read through connectors and exports, nothing is typed in them, and the hook asks me before any keystroke on such a page.

How much approval an act needs depends on what a mistake would cost. Experiments go ahead without asking, most work starts with a proposed plan, and outreach does nothing without an explicit yes. This site publishes once its checks pass: the prose check is clean, every new link has been opened, and the page has been viewed on a desktop and a phone in light and dark. A push to dexter, the public version of my workspace, waits for me to read the diff.

Try it

Have the model write into drafts, stop before every submit button, and hold no tool that sends. In Claude Code, a PreToolUse hook is a short script that can refuse a command by pattern, and it still applies in a session you forgot to watch. dexter's audit hook is one full version.

4Checks before I read

The errors that matter are the plausible ones. A citation can pair a real arXiv identifier with a title that only sounds right. A real number from a real paper can end up attached to the wrong measurement. An email can say my work is attached when the only file is a resume. Each of these reads well, so a person skimming the output lets it through, and I have the machine check for them before I read anything.

Code checks whatever can be checked mechanically. Before an email reaches me, a gate reads the draft back and fails it if it promises attachments it does not carry, keeps a placeholder, names a weekday that does not match its date, or says someone is copied when nobody is. Before any outreach, a second gate follows every cited paper to its page to confirm the title and that the person is an author, reads the person's own page for how they ask to be contacted, and searches my mail for an earlier thread with them.

The order of the checks matters too. In a research map the fact check runs before the style edit, since polishing an unchecked draft makes its errors read better.

Anything that can be executed gets executed. Every answer in a practice deck is run, along with its tests and a set of deliberately wrong answers that the tests have to catch. Every figure in a textbook computes the idea it shows, so the numbers in its caption come from the same math as the text.

The rest needs a reader who did not write the work. An agent reviewing its own draft brings the assumptions it wrote under, so finished work goes to fresh agents with no stake in it: one argues against it and looks for what is wrong, and another judges whether it holds. Outreach needs a pass from a fresh reader before I see it, and the pass expires after two days.

Try it

Open a new chat, paste in only the output and its sources, and ask what is wrong with it. When a model hands you an analysis, ask it for code that asserts each number the analysis states, then run the code yourself.

5Short named rules

Most of my preferences apply across many tasks, so I write each one once as a short file with a name and attach it to a request with a plus sign, as in "+ordering". At the start of a task the agent picks the rules that apply and names them in one line, which shows me how it has framed the work while a correction is still cheap. These five are the ones I would hand to anyone, and each is plain text that works pasted into any chat.

  • Ordering. Given N items, reading only the first M should give about the best M I could have read. The second item is chosen given the first, so two excellent items that make the same point are a bad pair. Sorting by score breaks this rule because it ranks each item alone, and saving the best for last breaks it because a reader may stop anywhere. The same rule orders a page, whose first paragraph should be its best one-paragraph version.
  • The five-minute idea. Every problem, paper or field turns on one idea that takes about five minutes to learn and unlocks far more than the problem itself. Find it, lead with it, and name two or three other problems it unlocks. Understanding an idea and implementing it are separate skills, and each gets its own practice.
  • Start small. Make something work at the smallest scale that can show it and look at the result: one or two generated items, then four or five, then the full run. Each step needs a result someone has read, a control at the same scale because small runs are noisy, and a one-line decision to scale up, fix or stop.
  • Method first. Present work the way a proof is presented, with the method shown on a small example before any results, so the reader can check each result as it arrives.
  • Plain prose. Machine-written text has habits, and I give each one a budget instead of banning words. The habits I watch most are defining a claim by what it is not, a balanced sentence that restates a whole design as a slogan, a label from an outline used as if the reader knew it, and a paragraph that ends on a quotable restatement of itself. A script counts them, and this page passes it.

Try it

Keep the five as text snippets and paste the ones that fit above a request. dexter's versions are written in full, and the prose script runs on any markdown file.

6Fewer, batched interruptions

Each question pulls me back into work I had handed off, so the agent's default is to act. It comes back to me for four things: a design decision where different answers would build materially different things and the code cannot settle it, a captcha, a credential, and a binding legal agreement. When it is blocked on one of these, it first finishes every piece of work that does not depend on the answer and then asks once, with every question in one batch.

Before I leave, I can hand the agent a window. "I'm going to sleep, take autonomy" gives it eight hours. It works through the deferred work in dependency order, settles design questions itself and writes each decision down, so a question it would have asked becomes a decision I review in the morning. It keeps everything committed at every stopping point, because the window can end at any moment and I read the result cold. Sends still wait for me.

Independent work runs in parallel and in the background, so no step waits on a command that could run behind it. Separate agents also keep the main conversation clean: a search across a codebase comes back as its conclusion, and the files it read stay out of the context. Every background job needs a place where its result lands and someone who reads it, since parallel work that nobody checks adds nothing. Long jobs run as sessions I can open, watch and take over.

Try it

Before a long task, tell the model the four things worth stopping for and ask for one batched list of questions at the end. When you step away, ask it to log every decision it would have asked you about.

7Deferred work on disk

Work that cannot happen yet goes into a queue on disk along with what it waits on. It stays blocked until those dependencies are done, and getting it done never depends on anyone remembering it. Each item is written so a fresh session could act on it alone, and its title starts with who acts next, the agent or me. I never file items by hand. Asking for something is enough for the agent to write the item, and a large item gets a follow-up checkpoint that depends on it.

Items sit in tiers inside time frames, from the next ten minutes to this term, and the queue hands out the shortest frame and the highest tier first. An item that blocks another is raised to the tier of the work it blocks, since that work cannot start without it. A session takes its next item and claims it in one step, so two sessions never take the same one, and I set priorities by dragging cards on a board.

Try it

Keep one todo file in which every line says what it waits on and who moves next, and have the model read it and propose the next item at the end of each task. dexter's queue is a single script.

8Privacy by where things are stored

A habit of leaving private data out of shared files holds until the one time it slips. So private material is kept where a slip cannot publish it: a separate repository with no remote, ignored by the shareable one, which holds my raw prompts, my own writing, other people's writing and my contacts. Data files are ignored everywhere, since a stray spreadsheet is where contact details tend to end up, and so are the folders where tasks keep personal details, such as the profile an application form is filled from.

Anything public is built from the private workspace by a script. An allowlist names what may go out, marked passages are dropped, private strings are redacted, and a scan fails the build on anything shaped like an email address, a phone number, an IP address or a key. A person reads the diff only after the scan passes. The pages under AI writing on this site go through a similar public step, which removes notes addressed to me and links to private pages.

Try it

Keep a private folder outside every repository you share, and publish by copying named files out of it. Before anything goes public, ask a model in a fresh chat to list every name, address, number and account that appears in it.

9What I use it for

Research maps

A team of agents maps a field from its problem hierarchy down to the open sub-problems, with a reading order and the companies working on each part, and the map is fact checked before it is edited. Flow matching and its descendants is one. For a single topic, a reading path picks each paper given the ones before it, following the ordering rule.

Textbooks and practice

A textbook states one idea per chapter, derives it, and builds it up in interactive figures that compute it on a small example; Fundamental Ideas from First Principles is the first. A practice deck shows on each card only what I would face at the start, orders its cards so that stopping anywhere leaves the best set, and runs every answer before I see it. To learn something new, I have the agent ask me one question at a time so I derive the idea myself, and a morning email teaches one new development in my corner of AI from first principles.

Applications and outreach

For applications, the agent finds companies worth applying to, picks how to reach each one, and leaves every email as a draft that has passed both gates. It fills application forms and stops at Submit. If I authorize a run to submit for me, it still checks before every Submit that no process with that company is under way, sends each essay to me first, and hands back any agreement that waives a right.

Coursework

I use it for a course only where that course allows AI. It reads my course sites and never submits, posts or marks an announcement read, and a deck for an exam is built from the course's own materials after reading its policy on AI.

Everyday work

It makes slides in my own style and checks every slide, transcribes photos of handwritten notes and checks each line against what the notes cover, finds the print page of a passage for a citation, and orders dinner up to the Place Order button.

10What stays with me

I sign in to every site myself, and no agent types a password, a two-factor code or a captcha, in an autonomy window or out of one. Questions only I can answer, such as how my name is pronounced, come back to me. I read every email before I send it and every diff before dexter is pushed. My own writing is under Writing, and work Claude writes at my direction is under AI writing, where each page says so.

11The setup behind this

All of this runs on Claude Code in one folder of plain files: the instructions for each task and their lessons, the named rules, memory, and the queue. I reach it from a terminal, from the Claude desktop app, and from my phone through a bot in a Discord server of my own, and it runs on a desktop at home that stays on, with my laptop as a standby. dexter is the open source version of that folder, with the hook, the gates, the lessons, the rules and the queue described above, for anyone who wants a starting point.
